# Rubric: is this reproduction package ready to post?

Every check reads the thing itself against the issue, never the write-up's shape. A long, confident, well formatted report gets no credit for being long, confident, or well formatted. A terse report that has the proof passes.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (see Environment in the evidence guide), read against the platform, version, and settings the issue says matter. | The report names the tool version and the OS/platform it ran on, plus every setting the issue or its thread says changes the failure (for example driver, shell, build profile, locale, backend). Fail if there is no environment record at all, or if a setting the issue calls out as relevant is missing. | required |
| version-faithful | The environment record compared against the version, platform, and channel the issue targets (issue body, thread highlights, repo-facts latest release). | The tested version and platform match what the issue targets, OR every difference is stated openly in the report. Fail if the report tested a different version, platform, or release channel than the issue and does not say so. | required |
| steps-rerunnable | The repro report's steps, from starting state to the triggering command. | A stranger with only public resources could re-run the steps and reach the trigger. Each input is either pasted in, or described exactly enough to recreate from the description plus the issue (for example "a minimal env.yml with a valid dependencies list plus a category: section", or "the issue's two format calls with ranges 19-32 and 18-31"). Fail if any needed step depends on private code, an unshared or unavailable file, or a vague instruction ("set up the project", "run it a few times", "the layout from the issue" when the issue does not contain it) with nothing concrete behind it. Fail if there are no steps. | required |
| trigger-matches | The input, command, expression, or config in the steps, compared line by line with the trigger the issue describes. | The steps exercise the same trigger the issue reports (same syntax, same operator, same expression, same config shape). Fail if the input was changed in a way that produces a different code path, such as a different range syntax, an unbound variable, or a swapped operator, even if the change looks small. When an input is described rather than pasted, compare the described shape with the issue's trigger; it matches if it contains the element the issue or thread says causes the failure. | required |
| artifact-shows-behavior | The artifacts in the repro report (pasted output, error text, exit codes, logs, captured responses) read against the symptom the issue describes. | The artifact itself shows the issue's specific symptom: the same error or panic class, the same wrong output, the same exit behavior. For a cannot-reproduce, the artifact shows the real attempt's actual output. Fail if there is no artifact, if the artifact only shows the tool starting or running normally, or if it shows a different symptom than the one claimed (for example a graceful validation error presented as a crash, or a process still alive presented as a crash). | required |
| claims-match-evidence | Every assertion in the claim comment and repro report (reproduced, confirmed, root cause, "guaranteed", "verified", scope such as "also happens on X"), each matched to an artifact in the report. The Expected and Actual lines compared with the artifacts. | The package's main result (reproduced, or could not reproduce) is backed by an artifact it shows, and Actual agrees with that artifact. Expected states what the issue says should happen; in a cannot-reproduce it may instead state what the issue predicts the attempt would show. Extra or contrast runs that are described but not pasted do not fail this check when the main result stands on its own artifacts; they are graded under control-run. Explanations worded as guesses ("appears", "may", "seems") are hypotheses and pass. An honest cannot-reproduce passes when it shows a real attempt and names what differed from the issue's setup. Fail on a root cause stated as fact, a certainty word used as proof ("guaranteed", "100%", "definitely"), or a scope claim ("also happens on X") that no shown artifact backs, or if Actual contradicts the artifacts. | required |
| claim-specific | The claim comment, read against the issue title and body. | The claim names something only true of this issue (the specific symptom, component, version, or input) and states a concrete next step that is investigation or testing. Fail if the comment could be pasted onto any other issue unchanged ("+1", "assign me", "I can work on this"), or if it promises a fix, a guaranteed outcome, or a delivery date. | required |
| ai-disclosure | The repo-facts contribution policy (any AI policy), then the claim comment and repro report. Treat every package as AI-assisted work. | If the repo's stated policy requires disclosing AI use in issues or comments, at least one of the comments discloses it, naming the assistance and its extent. If the repo has no AI policy, or its policy is permissive, or it only asks for disclosure in pull requests, this check passes. Fail only when the policy requires disclosure for comments or all contributions and neither comment discloses. | required |
| control-run | The repro report's steps and artifacts. | The report includes a contrast run (a working case, a different input, or a different config) whose output differs in the way the issue predicts. | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check fails or is unclear: proof I cannot verify is proof that is not ready to post. Preferred checks are reported but never change the verdict.

In live mode on a claim-only draft, the checks whose evidence is the repro report (env-recorded, version-faithful, steps-rerunnable, trigger-matches, artifact-shows-behavior, control-run) are reported as unclear with "not yet applicable: claim-only draft" and left out of the verdict. The verdict then rests on claims-match-evidence (read against the claim comment alone: it must not assert a reproduction it has not shown yet), claim-specific, and ai-disclosure.
