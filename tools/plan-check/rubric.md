# Rubric: is this plan ready to post and build from?

Every check reads the plan itself against the issue, the thread, and the repro evidence. Length, polish, and confidence earn nothing. A short plan that is grounded, bounded, buildable, and testable is ready. A long confident one that fails any of those is not.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause, read against every step, control run, debug output, and Expected/Actual line in the repro evidence (see Diagnosis and grounding in the evidence guide). | The plan names a cause, and that cause is consistent with everything the repro evidence shows. Fail if no cause is stated, or if any repro artifact rules the cause out: a control run where the blamed component works fine, a step showing the failure happens before the blamed code runs, or a timing or data result that points somewhere else. A cause the thread suggested still fails if the repro evidence contradicts it. | required |
| scope-bounded | The plan's in-scope and out-of-scope statements and every item in its approach, read against what the issue and repro evidence actually need fixed. | The plan is one bounded change aimed at the cause the evidence shows. Checking other paths that share the same code, adding a regression test for the issue's own cases, or explicitly deferring related work with a reason all pass. Fail if the plan also takes on work the issue does not need: a migration, a dependency upgrade, a rewrite or restructure, a new option or feature, UI changes, a CI or test-harness overhaul, or unrelated cleanup. This fails even when the core fix inside it is correct. | required |
| executable | The plan's files or code areas and its approach. | A stranger could start the work without asking the author anything: the plan names the file(s) or specific function or area it will change, and states one chosen approach. Fail if there are no files or areas, if the approach is left open ("whichever is easier", "somewhere", "not sure which layer", "profile and see"), or if the plan is only an intention to investigate. | required |
| test-decisive | The plan's test plan, read against the repro evidence's steps and Actual output. | The test plan names an observable outcome that would show this specific fix worked: the repro steps re-run with the changed result stated, or a regression test that asserts the issue's case. Fail if the only test is "run the full test suite", "should feel fast", "nothing else should break", or anything else that names no observable result for the fix itself. | required |
| thread-engaged | The thread highlights (or live thread), especially owner, maintainer, and collaborator comments, read against the candidate plan and the plan comment. | If the thread contains explicit maintainer direction (an identified culprit or file, a settled approach, a patched build or test request, a linked prior PR or fix attempt), the plan or comment engages it: it follows that direction, builds on it, or says why it departs. If the thread has no such direction, this check passes. Fail if the plan ignores explicit maintainer direction or proposes something that sidesteps it without saying so. | required |
| ai-disclosure | The repo-facts contribution policy (any AI policy), then the plan comment. Treat every package as AI-assisted work. | If the repo's stated policy requires disclosing AI use in comments or in all contributions, the plan comment discloses it, naming the tool and how it was used. If the repo has no AI policy, a permissive one, one that only asks for disclosure in pull requests, or a rule that comments must be in the author's own words with no disclosure ask, this check passes. Fail only when disclosure is required for comments or all contributions and the comment does not disclose. | required |
| unknowns-stated | The plan's risks and unknowns, and any confident claims in the plan and comment. | The plan names what it has not verified yet (an untested platform, a deferred variant, a behavior it still needs to check) instead of presenting guesses as settled. | preferred |

## Verdict rule

Accept if every required check passes. Reject if any required check fails or is unclear: a plan I cannot verify from the package is not ready to build from. The preferred check is reported but never changes the verdict.

In live mode the repro evidence is the student's own posted repro comment, as quoted in their drafts. If the drafts quote no repro evidence, diagnosis-grounded and test-decisive grade unclear, which counts as fail.
